# Limits and Error Codes

Generated from [`protocol-contract.json`](https://github.com/aceprotocol/ace-spec/blob/main/protocol-contract.json), the [constants of chapter 02](/docs/encoding#constants) and the [error codes of chapter 06](/docs/delivery#error-codes). Every SDK checks its constants against the contract.

## Wire identifiers

| Item | Value |
|---|---|
| Packet version (`ace`) | `"1"` |
| Signature domain | `ace.v1` |
| Signatures | `ml-dsa-65` (ML-DSA, FIPS 204) |
| Packet KEM | X-Wing, `draft-connolly-cfrg-xwing-kem-11` |
| Core message types | `ace:receipt:1`, `ace:contact:1` |
| Official profiles | `ace:core:1`, `ace:text:1`, `ace:commerce:1` |
| Relay authentication headers | `X-ACE-Audience`, `X-ACE-Nonce`, `X-ACE-Id`, `X-ACE-Timestamp`, `X-ACE-Seq`, `X-ACE-Signature` |

## Error codes

An SDK reports every failure as one error type carrying a `code`, whose category is fixed. `transient` and `local` failures are retryable; `permanent` ones are not.

| Category | Codes |
|---|---|
| `permanent` | `invalid_argument`, `invalid_packet`, `unsupported_version`, `wrong_recipient`, `invalid_signature`, `invalid_authorization`, `stale_timestamp`, `stale_peer_binding`, `decryption_failed`, `unknown_prekey`, `unsupported_schema`, `invalid_body`, `replay_horizon`, `invalid_kel`, `kel_conflict`, `unknown_peer`, `not_registered`, `not_permitted`, `relay_rejected`, `blocked_address`, `delivery_rejected`, `expired` |
| `transient` | `relay_unavailable`, `relay_protocol_error`, `fetch_failed` |
| `local` | `storage_failed`, `identity_unavailable`, `lock_busy`, `receiver_capacity`, `thread_busy` |

`delivery_rejected` carries the receipt's `code` as its remote code. Profile rules MAY raise further permanent codes matching the outcome-code grammar ([profiles/commerce.md](/docs/commerce#check-order) defines the commerce codes). Relay responses map to these codes as specified in [07](/docs/relay#client-rules).
